# Behavior Scenarios in the Editor: Point-to-Code Design

## Status

Architectural, brainstormed with the user 2026-09-28. Originated as a request to add a hover-driven
"point to code" action on Gherkin text in a Formal Spec review. Escalated to architectural once
exploration found: (1) no hover provider exists anywhere in this contrib folder, forcing a switch to
CodeLens (simpler: line-anchored, no debounce/cancellation, no new grammar needed); and (2) a deeper
gap — the Gherkin currently shown in a Formal Spec review is not the governed `behavior` field
sys-platform now stores; it is a separate, ephemeral preview regenerated by its own LLM call and
never written back. Closing that gap is this spec's real scope; the CodeLens is the last, smallest
piece built on top of it.

## Context

sys-platform (a sibling Rust repo) was just extended, in
`docs/superpowers/specs/2026-09-28-behavior-scenarios-design.md`, to store a Formal Spec's behavior
as real Gherkin text (field `behavior`), optionally paired with a structured `then` decision per
scenario (field `thenDecisions`), and to expose a `system-ontology candidates <workspace> <operation>`
command that lists real candidate functions per scenario, narrowed by class/type — never by name,
never verified, purely navigation. sys-editor (this repo) has not been touched to match: its
`SysFormalSpec` TypeScript type, its Formal Spec review rendering, and its scenario-preview flow all
predate this change and know nothing about `behavior`/`thenDecisions`.

## What exists today, verified by direct reading, not assumed

- `SysFormalSpec` (`common/sysFormalSpec.ts:35-53`) has no `behavior` or `thenDecisions` field.
  `parseFormalSpec` (`sysFormalSpec.ts:103-130`) builds a fresh object naming only known fields —
  any `behavior`/`thenDecisions` present in a raw JSON blob is silently dropped the moment it is
  parsed, even if a future model answer already includes them. This is the one change in this spec
  that is not optional: without it, nothing downstream can ever see this data.
- The Gherkin shown in a Formal Spec review page comes from `requestFormalSpecScenarios`
  (`common/sysFormalSpecScenarios.ts:9-23`), which POSTs the *source requirement text* to sidex-server's
  `/v1/sys/formal-spec-scenarios` endpoint and gets back freshly-generated Gherkin — explicitly
  documented as "regenerated for each review and never written back." This is a real, separate
  mechanism from the governed `behavior` field; today there is no code path where the two could even
  be the same text.
- `renderFormalSpecReview` (`common/sysFormalSpecReview.ts:55-109`) takes that ephemeral Gherkin as an
  optional `scenarios` parameter and fences it verbatim under `## Scenarios` (`scenarioSection`,
  lines 22-24). The whole page is a generated Markdown string, opened via
  `editorService.openEditor({resource})` (`browser/sysSemanticWorkbenchView.ts:332`) in VS Code's
  stock text editor — not a webview, not a custom editor.
- No `registerHoverProvider` or `registerCodeLensProvider` call exists anywhere under
  `src/vs/workbench/contrib/sys` today — confirmed by direct grep. Either feature needs new
  provider-registration code; there is no existing pattern in this folder to copy.
- `requestFormalSpec` (`common/sysFormalSpecDraft.ts:11-45`) sends only `{ model, intent, requestId }`
  to sidex-server's `/v1/sys/normalize-intent` — no schema/prompt text travels in this request.
  Confirmed with the user: sidex-server does not call back into sys-platform's
  `formal_spec_schema_guidance()`; it only relays a prompt to the LLM. Since the request carries no
  schema, sidex-server must hold its own copy of the Formal Spec schema/prompt template server-side —
  a real dependency this spec cannot design around, only name.

## Out of scope, explicitly: the sidex-server prompt

**sidex-server (a separate repo/service) must be updated, outside this spec, to actually ask the
model for `behavior` and `thenDecisions`** using guidance equivalent to what
`formal_spec_schema_guidance()` now teaches on the sys-platform side (the BEHAVIOR and THEN DECISIONS
sections added there 2026-09-28). Until that happens, every piece of sys-editor work below is
correctly wired but will simply never receive `behavior`/`thenDecisions` from a live normalize-intent
call — the type/parsing fix (below) makes the editor *capable* of holding this data the moment
sidex-server starts sending it; it does not make sidex-server send it. This is a blocking
prerequisite for the feature's practical usefulness, tracked here as a known dependency, not designed
or implemented in this repo.

## Design

### 1. Type and parsing (`common/sysFormalSpec.ts`)

`SysFormalSpec` gains two optional fields, both additive (an older record or an older sidex-server
response simply omits them, same pattern already used for `kind`/`entities`/`relationships`):

```typescript
export interface SysFormalSpecThenDecision {
	readonly scenario: string;
	readonly then: {
		readonly field: string;
		readonly becomes: string;
		readonly provenance: SysFormalSpecProvenance;
	};
}

// added to SysFormalSpec:
readonly behavior?: string;
readonly thenDecisions?: readonly SysFormalSpecThenDecision[];
```

`parseFormalSpec` gains matching optional-field handling (same `raw.X === undefined ? {} : {...}`
spread pattern already used for `entities`/`relationships`), with a `thenDecisions` validator
(`thenDecisions(value: unknown)`) mirroring `entities`'s shape-checking style: each entry must have a
non-empty `scenario` string and a `then` object with `field`/`becomes` strings and a valid
`provenance`. A present-but-malformed `thenDecisions` is rejected the same way a malformed `entities`
array is today (throws, caught by `requestFormalSpec`'s existing try/catch, surfaced as "The model's
answer does not match the Formal Spec contract").

### 2. Review rendering, with the fallback already agreed (`common/sysFormalSpecReview.ts` and its caller)

At the call site that currently always calls `requestFormalSpecScenarios` (wherever
`renderFormalSpecReview`'s `scenarios` argument is produced — inside the Semantic Workbench view's
review-building flow), the source of `scenarios` changes to:

- If `record.draft.behavior` is present and non-empty: use it directly. This is real, governed text —
  no network call, no LLM, no regeneration.
- Otherwise: fall back to `requestFormalSpecScenarios` exactly as today (confirmed: keep the fallback,
  not remove it — a Formal Spec drafted before sidex-server sends `behavior` still needs a review
  page).

`scenarioSection` itself needs one small addition: when the fallback path was used (not `behavior`),
prepend a one-line notice — "⚠ preview only — not yet part of the confirmed Formal Spec" — so a
reader never mistakes ephemeral, ungoverned preview text for the real, stored `behavior`. When
`behavior` was used directly, no such notice; it is the real thing.

### 3. CodeLens provider and command

**New file** `browser/sysBehaviorCodeLensProvider.ts`, a `languages.CodeLensProvider` registered via
`languages.registerCodeLensProvider({ pattern: '**/*.intent.review.md' }, provider)` in
`sys.contribution.ts` (same registration style already used there for other contributions).

`provideCodeLenses(document)`: scans `document.getText()` line by line, tracking whether the scan is
currently inside a ` ```gherkin ` fence (entered on a line that is exactly ` ```gherkin `, exited on
the next ` ``` `). Only inside that fence, a line matching `/^\s*(Scenario|Scenario Outline):\s*(.+)/`
becomes one `CodeLens` at that line's range, titled "Point to code", command id `sys.pointToCode`,
arguments `{ requirementId, scenarioName }` — `requirementId` read once from the document's first
line (`# {id} — Formal Spec review`, already the exact format `renderFormalSpecReview` emits at
line 74), `scenarioName` the captured text after the keyword, trimmed.

**New command** `sys.pointToCode(requirementId, scenarioName)`, registered alongside the provider:

1. Read the real Formal Spec record for `requirementId` via `projectService.readFormalSpec(id)`
   (`browser/sysProjectService.ts:230`, already used the same way at
   `sysSemanticWorkbenchView.ts:356,372`) — not a re-parse of the Markdown, which is a projection and
   could drift from the real JSON.
2. If its `operation` is null or unapproved, show an information message ("this requirement has no
   confirmed operation yet") and stop — never call the platform with a guess.
3. Call `system-ontology candidates <workspaceRoot> "<operation.value>"` via the same
   `TaskProcessTransport`-based subprocess pattern `readGoverned` already uses
   (`sysSemanticWorkbenchView.ts:157`).
4. Parse the JSON (`{ scenarios: [{ scenario, candidates, reason? }] }`), find the entry whose
   `scenario` equals `scenarioName`.
5. No matching entry, or `candidates` empty: show the `reason` (or a generic "no candidates found"
   if absent) as an information message. Never silently do nothing.
6. One or more candidates: show a **Quick Pick** (per the user's explicit choice — never jump
   straight to the first one, even when there is only one; consistency over false economy) listing
   `"{name} — {file}"` per candidate, with a `✓ then-observed` suffix on any candidate whose
   `thenObserved` is `true`. On selection, open that file (`vscode.open`-equivalent
   `editorService.openEditor`) at the candidate's `location` line if present, otherwise at the top of
   the file — never claim more precision than the data has.

## Files touched

- `common/sysFormalSpec.ts` — add `SysFormalSpecThenDecision`, `behavior`/`thenDecisions` fields,
  parsing/validation for both.
- `common/sysFormalSpecReview.ts` — `scenarioSection` gains the fallback-preview notice.
- The Semantic Workbench view's review-building call site — switch `scenarios` source to prefer
  `record.draft.behavior`, falling back to `requestFormalSpecScenarios`.
- `browser/sysBehaviorCodeLensProvider.ts` (new) — the CodeLens provider.
- `browser/sys.contribution.ts` — register the provider and the `sys.pointToCode` command.
- **Not touched, explicitly**: sidex-server (separate repo/service) — the prompt/schema update
  needed for `behavior`/`thenDecisions` to ever actually arrive from a live model call is a named,
  blocking prerequisite, not designed or implemented here.

## Review Focus

- A Formal Spec record with `behavior` present but empty/whitespace-only — must fall back to
  `requestFormalSpecScenarios`, not render an empty `## Scenarios` section as if it were real.
- A `.intent.review.md` file opened for a `DATA_MODEL`/`RELATIONSHIP` kind requirement (no
  `operation`, no scenarios section at all per `renderFormalSpecReview`'s branching) — the CodeLens
  provider must find zero matching lines and register zero lenses, not error.
- Two scenarios with the identical name inside one Feature (Gherkin allows this) — `sys.pointToCode`
  matching by `scenarioName` string would hit the first equal match only; worth a one-line note in
  the command's own code acknowledging this rather than silently mismatching (matches a known,
  already-accepted limitation on the sys-platform side for the same reason).
- The workspace-root/requirement-record lookup failing (e.g. the reviewed file was opened without an
  active sys project) — the command must degrade to an information message, never throw an unhandled
  exception into the editor's command palette.
- A `thenObserved: true` candidate must never be presented with any stronger affordance (a checkmark
  icon suggesting verification) than the rest of this session's UI already uses for
  honestly-uncertain state — reuse the existing "GOVERNED_NOT_CHECKED"-style plain-text voice, not a
  green-checkmark pattern, consistent with the sys-platform spec's own Review Focus on this exact
  point.
